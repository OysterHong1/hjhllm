# HJH LLM 趣味聊天室 PRD

## 1. 项目概述

本项目是一个轻量趣味聊天室。用户打开链接后，通过用户名完成假登录，进入一个类似 Claude / ChatGPT 的聊天界面。用户以为自己正在和一个会思考的 LLM 对话，实际回复由项目部署者在本地后台手动输入。

第一版不部署数据库、不做服务端会话、不做真实多用户实时通信。所有数据保存在浏览器 `localStorage` 中，以最低成本完成可玩的单机闭环。

## 2. 项目目标

### 2.1 核心目标

- 提供一个可以直接打开和使用的趣味聊天界面。
- 用户通过用户名完成假登录。
- 聊天记录保存在当前浏览器的 `localStorage`。
- 用户发送消息后，界面展示类 LLM 的 `Thinking...` 状态。
- 项目部署者可在同一浏览器的后台页面手动回复。
- 回复后用户聊天界面展示该回复。

### 2.2 非目标

- 不接入真实 LLM。
- 不接入数据库。
- 不实现真实账号系统。
- 不实现跨设备同步。
- 不实现真实多人在线聊天。
- 不实现 WebSocket、轮询 API 或实时服务。
- 不实现复杂管理员权限。

## 3. 目标用户

### 3.1 普通体验者

通过链接进入项目，输入任意用户名即可开始聊天。用户侧重点是体验“一个假装在思考的 LLM”。

### 3.2 项目部署者

通过本地后台页面查看当前浏览器中保存的会话，并手动写入回复。

## 4. 用户路径

### 4.1 普通用户路径

1. 用户点击链接。
2. 用户进入登录页。
3. 用户输入用户名。
4. 系统将用户信息写入 `localStorage`。
5. 用户进入聊天页。
6. 用户输入消息并发送。
7. 页面展示用户消息。
8. 页面在助手位置展示 `Thinking...`。
9. 项目部署者进入后台手动回复。
10. 用户回到聊天页或页面自动读取本地数据后看到回复。

### 4.2 部署者路径

1. 部署者访问 `/admin`。
2. 后台读取 `localStorage` 中的用户、会话和消息。
3. 后台展示待回复会话。
4. 部署者选择会话。
5. 部署者输入回复。
6. 回复被写入同一份 `localStorage` 数据。
7. 用户聊天页展示回复。

## 5. 页面结构

### 5.1 `/login`

- 用户名输入框。
- 进入聊天按钮。
- 如果本地已有用户，可直接进入聊天页。

### 5.2 `/chat`

- 左侧：历史会话列表。
- 右侧：当前会话消息区。
- 底部：消息输入框。
- 顶部或侧边：新建会话入口。
- 当前会话最后一条消息来自用户时，展示 `Thinking...`。

### 5.3 `/admin`

- 会话列表。
- 待回复会话标记。
- 会话详情。
- 回复输入框。
- 清空演示数据入口。

第一版管理员页面不做正式登录。可使用一个轻量入口提示，例如“仅部署者使用”。

## 6. 功能需求

### 6.1 假登录

- 用户名不能为空。
- 登录后生成本地用户对象。
- 用户对象保存到 `localStorage`。
- 再次打开页面时，如果本地存在用户对象，可直接进入聊天页。
- 可提供“切换用户”或“退出”按钮，清除当前用户。

### 6.2 会话管理

- 用户可新建会话。
- 会话标题默认取第一条用户消息的前 12-20 个字符。
- 会话按更新时间倒序展示。
- 当前用户只展示自己的会话。
- 管理员页面可展示本地保存的全部会话。

### 6.3 消息发送

- 支持三类消息：语音/文本/图片
- 空消息不可发送。
- 用户消息发送后立即写入 `localStorage`。
- 消息发送后输入框清空。
- 会话更新时间随消息更新。

### 6.4 Thinking 状态

Thinking 不作为真实消息保存，只由当前会话消息状态推导。

展示规则：

- 如果当前会话最后一条消息来自 `user`，展示 `Thinking...`。
- 如果当前会话最后一条消息来自 `admin`，不展示 Thinking。
- 如果当前会话没有消息，不展示 Thinking。

表现形式：

- 显示在助手回复位置。
- 点号可循环变化：`Thinking.`、`Thinking..`、`Thinking...`。
- 样式应弱于真实消息，像一个正在生成的占位状态。

### 6.5 本地管理员回复

- 管理员页面读取所有本地会话。
- 待回复会话应有明显标记。
- 管理员选择会话后可看到完整消息。
- 管理员输入回复后，写入一条 `admin` 消息。
- 回复写入后，该会话不再显示 Thinking。

### 6.6 本地持久化

所有核心数据保存在一个 `localStorage` key 中，建议命名为：

```text
hjhllm.store
```

数据包括：

- 当前用户。
- 用户列表。
- 会话列表。
- 消息列表。

第一版不考虑跨浏览器、跨设备或多用户真实同步。

## 7. 数据结构

### 7.1 Store

```ts
type Store = {
  currentUserId: string | null;
  users: User[];
  conversations: Conversation[];
  messages: Message[];
};
```

### 7.2 User

```ts
type User = {
  id: string;
  username: string;
  createdAt: string;
};
```

### 7.3 Conversation

```ts
type Conversation = {
  id: string;
  userId: string;
  title: string;
  createdAt: string;
  updatedAt: string;
};
```

### 7.4 Message

```ts
type Message = {
  id: string;
  conversationId: string;
  sender: "user" | "admin";
  content: string;
  createdAt: string;
};
```

## 8. 体验设计

### 8.1 视觉方向

整体参考 Claude：

- 浅色背景。
- 安静、内容优先。
- 左侧会话栏，右侧聊天主区。
- 输入区固定在底部。
- 不做营销首页。
- 不使用复杂动效。

### 8.2 聊天体验

- 打开后尽快进入聊天。
- 消息行宽适中，便于阅读。
- 用户消息和管理员回复需要有清晰视觉差异。
- Thinking 状态应自然出现在对话流中。
- 移动端可先简化为顶部会话选择，不强求复杂抽屉。

### 8.3 后台体验

- 后台要能快速看到哪些会话待回复。
- 待回复会话优先排序。
- 回复框要始终靠近当前会话。
- 清空数据功能需要二次确认。

## 9. 技术选型

### 9.1 推荐选型

- 应用框架：Next.js 或 Vite + React。
- UI：React + Tailwind CSS。
- 数据持久化：`localStorage`。
- 部署：Vercel 静态部署即可。

### 9.2 选型理由

- 趣味项目优先降低复杂度。
- `localStorage` 足够支持假登录和本地会话演示。
- 不部署数据库可以减少配置、费用和维护成本。
- 后续如果真的需要多人同步，再迁移到数据库或实时服务。

## 10. 验收标准

MVP 完成时应满足：

- 用户可输入用户名进入聊天。
- 用户可新建会话。
- 用户可发送消息。
- 发送消息后出现 `Thinking...`。
- `/admin` 可看到本地会话。
- `/admin` 可对会话写入回复。
- 回复后 `/chat` 可展示管理员回复。
- 刷新页面后，本地历史记录仍存在。
- 可清空本地演示数据。
- 项目可部署到 Vercel。

## 11. 后续可能扩展

- 增加假模型名和假推理阶段。
- 增加预设快捷回复。
- 增加导入 / 导出 JSON。
- 增加轻量密码保护 `/admin`。
- 增加浏览器通知或提示音。
- 在需求变大后再接数据库和真实同步。
